\hypertarget{md_doc_2cryptographic__documentation_autotoc_md84}{}\doxysection{\texorpdfstring{Principes généraux}{Principes généraux}}\label{md_doc_2cryptographic__documentation_autotoc_md84}
Win\+ConveyoR manipule des données sensibles à plusieurs niveaux \+: authentification des utilisateurs auprès de l\textquotesingle{}API, transfert de paquets depuis les miroirs, et vérification de l\textquotesingle{}intégrité des fichiers {\ttfamily .WIZARD}. La stratégie cryptographique du projet repose sur trois principes \+:


\begin{DoxyItemize}
\item {\bfseries{Aucune implémentation maison.}} Tous les algorithmes cryptographiques proviennent d\textquotesingle{}Open\+SSL, une bibliothèque auditée et maintenue. Les erreurs d\textquotesingle{}implémentation cryptographique sont la première source de vulnérabilités dans les outils de distribution logicielle.
\item {\bfseries{Défense en profondeur.}} Chaque couche (stockage, transport, intégrité) applique ses propres mécanismes de protection indépendamment des autres.
\item {\bfseries{Principe du moindre privilège.}} Les secrets (mots de passe, clés) ne sont jamais exposés en clair dans les logs, les configurations, ou les messages d\textquotesingle{}erreur.
\end{DoxyItemize}

\hypertarget{md_doc_2cryptographic__documentation_autotoc_md86}{}\doxysection{\texorpdfstring{Stockage des mots de passe API}{Stockage des mots de passe API}}\label{md_doc_2cryptographic__documentation_autotoc_md86}
\hypertarget{md_doc_2cryptographic__documentation_autotoc_md87}{}\doxysubsection{\texorpdfstring{Contexte}{Contexte}}\label{md_doc_2cryptographic__documentation_autotoc_md87}
L\textquotesingle{}API REST de Win\+ConveyoR nécessite une authentification pour les opérations privilégiées (publication de paquets, administration des miroirs). Les mots de passe des comptes API doivent être stockés de manière sécurisée côté serveur.\hypertarget{md_doc_2cryptographic__documentation_autotoc_md88}{}\doxysubsection{\texorpdfstring{Algorithme de hachage — bcrypt}{Algorithme de hachage — bcrypt}}\label{md_doc_2cryptographic__documentation_autotoc_md88}

\hypertarget{md_doc_2cryptographic__documentation_autotoc_md89}{}\doxysubsubsection{\texorpdfstring{Pourquoi bcrypt ?}{Pourquoi bcrypt ?}}\label{md_doc_2cryptographic__documentation_autotoc_md89}

\begin{DoxyItemize}
\item {\bfseries{Résistance au brute-\/force.}} bcrypt est un algorithme volontairement lent (« key derivation function »). Le paramètre de coût ({\ttfamily work factor}) contrôle le nombre d\textquotesingle{}itérations internes, rendant chaque tentative de brute-\/force exponentiellement plus coûteuse.
\item {\bfseries{Sel intégré.}} Chaque hash bcrypt embarque un sel aléatoire de 128 bits, éliminant les attaques par rainbow tables. Deux utilisateurs avec le même mot de passe produisent des hash différents.
\item {\bfseries{Résistance aux GPU.}} L\textquotesingle{}algorithme Blowfish sous-\/jacent de bcrypt est memory-\/hard, ce qui rend l\textquotesingle{}accélération par GPU ou ASIC significativement moins efficace que pour SHA-\/256 ou MD5.
\end{DoxyItemize}\hypertarget{md_doc_2cryptographic__documentation_autotoc_md90}{}\doxysubsubsection{\texorpdfstring{Paramètres de configuration}{Paramètres de configuration}}\label{md_doc_2cryptographic__documentation_autotoc_md90}

\hypertarget{md_doc_2cryptographic__documentation_autotoc_md91}{}\doxysubsubsection{\texorpdfstring{Pourquoi pas Argon2 ?}{Pourquoi pas Argon2 ?}}\label{md_doc_2cryptographic__documentation_autotoc_md91}

\begin{DoxyItemize}

\item Son format de hash est universellement reconnu par les outils d\textquotesingle{}audit et de migration.
\item Le work factor 12 est suffisant pour le modèle de menaces d\textquotesingle{}un gestionnaire de paquets (le vecteur d\textquotesingle{}attaque principal n\textquotesingle{}est pas le brute-\/force de mots de passe API mais la compromission de paquets).

Pour les sessions persistantes, le client stocke un {\bfseries{JWT (JSON Web Token)}} signé, jamais le mot de passe \+:


\begin{DoxyItemize}
\item {\bfseries{Windows}} \+: le token est stocké dans le {\bfseries{Windows Credential Manager}} via l\textquotesingle{}API {\ttfamily Cred\+Write}/{\ttfamily Cred\+Read}, qui chiffre les données avec DPAPI (Data Protection API), lié au compte Windows de l\textquotesingle{}utilisateur.
\item {\bfseries{Linux/\+WSL}} \+: le token est stocké dans un fichier {\ttfamily \texorpdfstring{$\sim$}{\string~}/.config/wconr/credentials} avec permissions {\ttfamily 600} (lecture/écriture propriétaire uniquement). Un avertissement est émis si les permissions sont trop permissives.
\item {\bfseries{Variables d\textquotesingle{}environnement}} \+: le token peut être passé via {\ttfamily WCONR\+\_\+\+API\+\_\+\+TOKEN} pour les environnements CI/\+CD, sans persistance sur disque.

\hypertarget{md_doc_2cryptographic__documentation_autotoc_md98}{}\doxysubsubsection{\texorpdfstring{Pourquoi un schéma hybride ?}{Pourquoi un schéma hybride ?}}\label{md_doc_2cryptographic__documentation_autotoc_md98}
Le chiffrement asymétrique (RSA) et symétrique (AES) ont des forces complémentaires. Les combiner permet d\textquotesingle{}exploiter les avantages de chacun tout en compensant leurs faiblesses respectives \+:


\begin{DoxyItemize}
\item {\bfseries{RSA seul est trop lent.}} Le chiffrement RSA est environ 1000x plus lent qu\textquotesingle{}AES pour le traitement de données brutes. Chiffrer des paquets {\ttfamily .WIZARD} de plusieurs Mo en RSA pur serait prohibitif en termes de performance.
\item {\bfseries{AES seul pose un problème de distribution de clé.}} AES est un algorithme symétrique \+: les deux parties doivent posséder la même clé secrète. Sans mécanisme d\textquotesingle{}échange sécurisé, cette clé devrait être partagée à l\textquotesingle{}avance, ce qui est impraticable pour un réseau ouvert de miroirs.
\item {\bfseries{RSA + AES résout les deux problèmes.}} RSA sécurise l\textquotesingle{}échange d\textquotesingle{}une clé AES éphémère, puis AES chiffre les données à haute vitesse avec cette clé.
\end{DoxyItemize}\hypertarget{md_doc_2cryptographic__documentation_autotoc_md99}{}\doxysubsection{\texorpdfstring{RSA — Échange de clés}{RSA — Échange de clés}}\label{md_doc_2cryptographic__documentation_autotoc_md99}
\hypertarget{md_doc_2cryptographic__documentation_autotoc_md100}{}\doxysubsubsection{\texorpdfstring{Fonctionnement}{Fonctionnement}}\label{md_doc_2cryptographic__documentation_autotoc_md100}
Chaque serveur miroir possède une {\bfseries{paire de clés RSA}} (clé publique + clé privée). La clé publique est distribuée aux clients, la clé privée reste exclusivement sur le serveur.

Lors de l\textquotesingle{}établissement d\textquotesingle{}une session WCR \+:


\begin{DoxyEnumerate}
\item Le client génère une {\bfseries{clé AES-\/256 aléatoire}} (256 bits) pour la session, appelée {\bfseries{session key}}.
\item Le client chiffre cette session key avec la {\bfseries{clé publique RSA}} du serveur miroir.
\item Le client envoie la session key chiffrée au serveur.
\item Le serveur déchiffre la session key avec sa {\bfseries{clé privée RSA}}.
\item Les deux parties possèdent maintenant la même clé AES-\/256 pour la suite de la communication.
\end{DoxyEnumerate}

\hypertarget{md_doc_2cryptographic__documentation_autotoc_md102}{}\doxysubsubsection{\texorpdfstring{Pourquoi RSA et pas ECDH (courbes elliptiques) ?}{Pourquoi RSA et pas ECDH (courbes elliptiques) ?}}\label{md_doc_2cryptographic__documentation_autotoc_md102}
RSA est un algorithme éprouvé depuis 1977, massivement audité, et dont les propriétés de sécurité sont bien comprises. Les courbes elliptiques (ECDH/\+ECDSA) offrent des clés plus courtes pour un niveau de sécurité équivalent, mais RSA est retenu pour Win\+ConveyoR car \+:


\begin{DoxyItemize}
\item Sa simplicité conceptuelle facilite l\textquotesingle{}audit et le debugging du protocole.
\item Son support dans Open\+SSL est mature et stable sur toutes les plateformes cibles.
\item La taille des clés n\textquotesingle{}est pas un facteur limitant pour WCR (l\textquotesingle{}échange de clés est ponctuel, pas répété par frame).
\end{DoxyItemize}\hypertarget{md_doc_2cryptographic__documentation_autotoc_md103}{}\doxysubsection{\texorpdfstring{AES-\/256 — Chiffrement des données}{AES-256 — Chiffrement des données}}\label{md_doc_2cryptographic__documentation_autotoc_md103}

Chaque frame contient un {\bfseries{IV (Initialization Vector)}} unique de 16 octets (128 bits), généré aléatoirement via {\ttfamily RAND\+\_\+bytes()}. L\textquotesingle{}IV garantit que deux frames identiques produisent des ciphertexts différents, empêchant les attaques par analyse de patterns.\hypertarget{md_doc_2cryptographic__documentation_autotoc_md105}{}\doxysubsubsection{\texorpdfstring{Pourquoi AES-\/256 ?}{Pourquoi AES-256 ?}}\label{md_doc_2cryptographic__documentation_autotoc_md105}

\begin{DoxyItemize}
\item {\bfseries{Standard mondial.}} AES (Advanced Encryption Standard) est le standard de chiffrement symétrique adopté par le NIST en 2001. Il est utilisé par les gouvernements, les institutions financières, et la quasi-\/totalité des protocoles de communication sécurisés.
\item {\bfseries{Sécurité 256 bits.}} AES-\/256 offre une marge de sécurité maximale parmi les variantes AES (128, 192, 256). Même avec les avancées théoriques (attaques biclique), la complexité effective reste à \texorpdfstring{$\sim$}{\string~}254.4 bits, largement hors de portée.
\item {\bfseries{Performance.}} Les processeurs modernes disposent d\textquotesingle{}instructions dédiées AES-\/\+NI (Intel/\+AMD) qui accélèrent le chiffrement/déchiffrement AES de manière matérielle, atteignant des débits de plusieurs Go/s. C\textquotesingle{}est essentiel pour le transfert de paquets {\ttfamily .WIZARD} volumineux.
\item {\bfseries{Blocs de 128 bits.}} AES opère sur des blocs de 128 bits (16 octets), ce qui est adapté aux frames WCR binaires sans overhead excessif de padding.
\end{DoxyItemize}\hypertarget{md_doc_2cryptographic__documentation_autotoc_md106}{}\doxysubsubsection{\texorpdfstring{Modes de chiffrement}{Modes de chiffrement}}\label{md_doc_2cryptographic__documentation_autotoc_md106}

Chaque paquet {\ttfamily .WIZARD} doit être vérifié pour garantir que son contenu n\textquotesingle{}a pas été altéré entre la publication et l\textquotesingle{}installation. Le checksum est le mécanisme central de cette vérification.\hypertarget{md_doc_2cryptographic__documentation_autotoc_md114}{}\doxysubsection{\texorpdfstring{Algorithme — SHA-\/256}{Algorithme — SHA-256}}\label{md_doc_2cryptographic__documentation_autotoc_md114}
Win\+ConveyoR utilise {\bfseries{SHA-\/256}} (SHA-\/2 family, 256 bits) pour tous les calculs de checksums \+:\hypertarget{md_doc_2cryptographic__documentation_autotoc_md115}{}\doxysubsubsection{\texorpdfstring{Pourquoi SHA-\/256 ?}{Pourquoi SHA-256 ?}}\label{md_doc_2cryptographic__documentation_autotoc_md115}

\begin{DoxyItemize}
\item {\bfseries{Résistance aux collisions.}} Aucune collision SHA-\/256 n\textquotesingle{}a été trouvée à ce jour. La complexité théorique d\textquotesingle{}une attaque par anniversaire est de 2\texorpdfstring{$^\wedge$}{\string^}128 opérations, bien au-\/delà de toute capacité de calcul actuelle.
\item {\bfseries{Standard universel.}} SHA-\/256 est utilisé par Git, Bitcoin, TLS, et la majorité des gestionnaires de paquets (apt, npm, pip). Son adoption massive signifie qu\textquotesingle{}il est constamment scruté et audité par la communauté cryptographique.
\item {\bfseries{Performance.}} SHA-\/256 bénéficie d\textquotesingle{}extensions matérielles (Intel SHA-\/\+NI, ARM SHA2) sur les processeurs modernes, permettant un débit de hachage de plusieurs Go/s.
\item {\bfseries{Taille de digest adaptée.}} 256 bits (32 octets) offrent un niveau de sécurité suffisant (128 bits de résistance aux collisions) tout en restant compact dans les structures binaires et les affichages hexadécimaux (64 caractères).
\end{DoxyItemize}\hypertarget{md_doc_2cryptographic__documentation_autotoc_md116}{}\doxysubsubsection{\texorpdfstring{Pourquoi pas SHA-\/512 ou SHA-\/3 ?}{Pourquoi pas SHA-512 ou SHA-3 ?}}\label{md_doc_2cryptographic__documentation_autotoc_md116}
SHA-\/512 offre une marge de sécurité supérieure mais au prix d\textquotesingle{}un digest plus volumineux (64 octets vs 32) qui augmente la taille des index de paquets sans bénéfice pratique pour le modèle de menaces de Win\+ConveyoR. SHA-\/3 (Keccak) est une alternative viable mais son support matériel est moins répandu que SHA-\/2, et l\textquotesingle{}écosystème (outils, documentation) est plus mature autour de SHA-\/256.\hypertarget{md_doc_2cryptographic__documentation_autotoc_md117}{}\doxysubsection{\texorpdfstring{Implémentation dans libwconr}{Implémentation dans libwconr}}\label{md_doc_2cryptographic__documentation_autotoc_md117}

Le champ {\ttfamily algorithm} permet une migration future vers un autre algorithme sans casser le format \+: le parser sélectionne la fonction de hash en fonction de cette valeur. Le champ {\ttfamily scope} indique si le hash couvre uniquement le payload ou l\textquotesingle{}intégralité du fichier (header + metadata + payload), permettant des stratégies de vérification différentes selon le contexte.

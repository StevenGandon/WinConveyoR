Cookies are {\ttfamily \doxylink{no-clobber_8d_a55aa2dc823b414005b6ab9f51301106d}{name}=contents} pairs that an \doxylink{structHTTP}{HTTP} server tells the client to hold and then the client sends back those to the server on subsequent requests to the same domains and paths for which the cookies were set.

Cookies are either "{}session cookies"{} which typically are forgotten when the session is over which is often translated to equal when browser quits, or the cookies are not session cookies they have expiration dates after which the client will throw them away.

Cookies are set to the client with the Set-\/\+Cookie\+: header and are sent to servers with the \doxylink{structCookie}{Cookie}\+: header.

For a long time, the only spec explaining how to use cookies was the original \href{https://curl.se/rfc/cookie_spec.html}{\texttt{Netscape spec from 1994}}.

In 2011, \href{https://www.ietf.org/rfc/rfc6265.txt}{\texttt{RFC6265}} was finally published and details how cookies work within \doxylink{structHTTP}{HTTP}. In 2016, an update which added support for prefixes was \href{https://datatracker.ietf.org/doc/html/draft-ietf-httpbis-cookie-prefixes-00}{\texttt{proposed}}, and in 2017, another update was \href{https://datatracker.ietf.org/doc/html/draft-ietf-httpbis-cookie-alone-01}{\texttt{drafted}} to deprecate modification of \textquotesingle{}secure\textquotesingle{} cookies from non-\/secure origins. Both of these drafts have been incorporated into a proposal to \href{https://datatracker.ietf.org/doc/html/draft-ietf-httpbis-rfc6265bis-02}{\texttt{replace}} RFC6265. \doxylink{structCookie}{Cookie} prefixes and secure cookie modification protection has been implemented by curl.\hypertarget{md_lib_2libwconr_2build_2__deps_2curl-src_2docs_2HTTP-COOKIES_autotoc_md1698}{}\doxysection{\texorpdfstring{Cookies saved to disk}{Cookies saved to disk}}\label{md_lib_2libwconr_2build_2__deps_2curl-src_2docs_2HTTP-COOKIES_autotoc_md1698}
Netscape once created a file format for storing cookies on disk so that they would survive browser restarts. curl adopted that file format to allow sharing the cookies with browsers, only to see browsers move away from that format. Modern browsers no longer use it, while curl still does.

The Netscape cookie file format stores one cookie per physical line in the file with a bunch of associated meta data, each field separated with TAB. That file is called the cookie jar in curl terminology.

When libcurl saves a cookie jar, it creates a file header of its own in which there is a URL mention that will link to the web version of this document.\hypertarget{md_lib_2libwconr_2build_2__deps_2curl-src_2docs_2HTTP-COOKIES_autotoc_md1699}{}\doxysection{\texorpdfstring{Cookie file format}{Cookie file format}}\label{md_lib_2libwconr_2build_2__deps_2curl-src_2docs_2HTTP-COOKIES_autotoc_md1699}
The cookie file format is text based and stores one cookie per line. Lines that start with {\ttfamily \#} are treated as comments.

Each line that specifies a single cookie consists of seven text fields separated with TAB characters. A valid line must end with a newline character.\hypertarget{md_lib_2libwconr_2build_2__deps_2curl-src_2docs_2HTTP-COOKIES_autotoc_md1700}{}\doxysubsection{\texorpdfstring{Fields in the file}{Fields in the file}}\label{md_lib_2libwconr_2build_2__deps_2curl-src_2docs_2HTTP-COOKIES_autotoc_md1700}

curl has a full cookie "{}engine"{} built in. If you just activate it, you can have curl receive and send cookies exactly as mandated in the specs.

Command line options\+:

{\ttfamily -\/b, -\/-\/cookie}

tell curl a file to read cookies from and start the cookie engine, or if it is not a file it will pass on the given string. {\ttfamily -\/b \doxylink{no-clobber_8d_a55aa2dc823b414005b6ab9f51301106d}{name}=var} works and so does {\ttfamily -\/b cookiefile}.

{\ttfamily -\/\doxylink{smooth-gtk-thread_8c_a37d972ae0b47b9099e30983131d31916}{j}, -\/-\/junk-\/session-\/cookies}

when used in combination with -\/b, it will skip all "{}session cookies"{} on load so as to appear to start a new cookie session.

{\ttfamily -\/c, -\/-\/cookie-\/jar}

tell curl to start the cookie engine and write cookies to the given file after the \doxylink{compressed_8d_ad77a8bf6bf91f4e7f4a9a017f6c7e68e}{request(s)}\hypertarget{md_lib_2libwconr_2build_2__deps_2curl-src_2docs_2HTTP-COOKIES_autotoc_md1702}{}\doxysection{\texorpdfstring{Cookies with libcurl}{Cookies with libcurl}}\label{md_lib_2libwconr_2build_2__deps_2curl-src_2docs_2HTTP-COOKIES_autotoc_md1702}
libcurl offers several ways to enable and interface the cookie engine. These options are the ones provided by the native API. libcurl bindings may offer access to them using other means.

{\ttfamily CURLOPT\+\_\+\+COOKIE}

Is used when you want to specify the exact contents of a cookie header to send to the server.

{\ttfamily CURLOPT\+\_\+\+COOKIEFILE}

Tell libcurl to activate the cookie engine, and to read the initial set of cookies from the given file. Read-\/only.

{\ttfamily CURLOPT\+\_\+\+COOKIEJAR}

Tell libcurl to activate the cookie engine, and when the easy handle is closed save all known cookies to the given cookie jar file. Write-\/only.

{\ttfamily CURLOPT\+\_\+\+COOKIELIST}

Provide detailed information about a single cookie to add to the internal storage of cookies. Pass in the cookie as an \doxylink{structHTTP}{HTTP} header with all the details set, or pass in a line from a Netscape cookie file. This option can also be used to flush the cookies etc.

{\ttfamily CURLOPT\+\_\+\+COOKIESESSION}

Tell libcurl to ignore all cookies it is about to load that are session cookies.

{\ttfamily \doxylink{curl_8h_aabc03ec968a2fdccde5c6709f712dd7ba500b467f799c735b639a78ca87b17fb6}{CURLINFO\+\_\+\+COOKIELIST}}

Extract cookie information from the internal cookie storage as a linked list.\hypertarget{md_lib_2libwconr_2build_2__deps_2curl-src_2docs_2HTTP-COOKIES_autotoc_md1703}{}\doxysection{\texorpdfstring{Cookies with Java\+Script}{Cookies with Java\+Script}}\label{md_lib_2libwconr_2build_2__deps_2curl-src_2docs_2HTTP-COOKIES_autotoc_md1703}
These days a lot of the web is built up by Java\+Script. The web browser loads complete programs that render the page you see. These Java\+Script programs can also set and access cookies.

Since curl and libcurl are plain \doxylink{structHTTP}{HTTP} clients without any knowledge of or capability to handle Java\+Script, such cookies will not be detected or used.

Often, if you want to mimic what a browser does on such websites, you can record web browser \doxylink{structHTTP}{HTTP} traffic when using such a site and then repeat the cookie operations using curl or libcurl.

\chapter{How to do code reviews for curl }
\hypertarget{md_lib_2libwconr_2build_2__deps_2curl-src_2docs_2CODE__REVIEW}{}\label{md_lib_2libwconr_2build_2__deps_2curl-src_2docs_2CODE__REVIEW}\index{How to do code reviews for curl@{How to do code reviews for curl}}
\label{md_lib_2libwconr_2build_2__deps_2curl-src_2docs_2CODE__REVIEW_autotoc_md1487}%
\Hypertarget{md_lib_2libwconr_2build_2__deps_2curl-src_2docs_2CODE__REVIEW_autotoc_md1487}%


Anyone and everyone is encouraged and welcome to review code submissions in curl. This is a guide on what to check for and how to perform a successful code review.\hypertarget{md_lib_2libwconr_2build_2__deps_2curl-src_2docs_2CODE__REVIEW_autotoc_md1488}{}\doxysection{\texorpdfstring{All submissions should get reviewed}{All submissions should get reviewed}}\label{md_lib_2libwconr_2build_2__deps_2curl-src_2docs_2CODE__REVIEW_autotoc_md1488}
All pull requests and patches submitted to the project should be reviewed by at least one experienced curl maintainer before that code is accepted and merged.\hypertarget{md_lib_2libwconr_2build_2__deps_2curl-src_2docs_2CODE__REVIEW_autotoc_md1489}{}\doxysection{\texorpdfstring{Let the tools and tests take the first rounds}{Let the tools and tests take the first rounds}}\label{md_lib_2libwconr_2build_2__deps_2curl-src_2docs_2CODE__REVIEW_autotoc_md1489}
On initial pull requests, let the tools and tests do their job first and then start out by helping the submitter understand the test failures and tool alerts.\hypertarget{md_lib_2libwconr_2build_2__deps_2curl-src_2docs_2CODE__REVIEW_autotoc_md1490}{}\doxysection{\texorpdfstring{How to provide feedback to author}{How to provide feedback to author}}\label{md_lib_2libwconr_2build_2__deps_2curl-src_2docs_2CODE__REVIEW_autotoc_md1490}
Be nice. Ask questions. Provide examples or suggestions of improvements. Assume the best intentions. Remember language barriers.

All first-\/time contributors can become regulars. Let\textquotesingle{}s help them go there.\hypertarget{md_lib_2libwconr_2build_2__deps_2curl-src_2docs_2CODE__REVIEW_autotoc_md1491}{}\doxysection{\texorpdfstring{Is this a change we want?}{Is this a change we want?}}\label{md_lib_2libwconr_2build_2__deps_2curl-src_2docs_2CODE__REVIEW_autotoc_md1491}
If this is not a change that seems to be aligned with the project\textquotesingle{}s path forward and as such cannot be accepted, inform the author about this sooner rather than later. Do it gently and explain why and possibly what could be done to make it more acceptable.\hypertarget{md_lib_2libwconr_2build_2__deps_2curl-src_2docs_2CODE__REVIEW_autotoc_md1492}{}\doxysection{\texorpdfstring{API/\+ABI stability or changed behavior}{API/\+ABI stability or changed behavior}}\label{md_lib_2libwconr_2build_2__deps_2curl-src_2docs_2CODE__REVIEW_autotoc_md1492}
Changing the API and the ABI may be fine in a change but it needs to be done deliberately and carefully. If not, a reviewer must help the author to realize the mistake.

curl and libcurl are similarly strict on not modifying existing behavior. API and ABI stability is not enough, the behavior should also remain intact as far as possible.\hypertarget{md_lib_2libwconr_2build_2__deps_2curl-src_2docs_2CODE__REVIEW_autotoc_md1493}{}\doxysection{\texorpdfstring{Code style}{Code style}}\label{md_lib_2libwconr_2build_2__deps_2curl-src_2docs_2CODE__REVIEW_autotoc_md1493}
Most code style nits are detected by checksrc but not all. Only leave remarks on style deviation once checksrc does not find anymore.

Minor nits from fresh submitters can also be handled by the maintainer when merging, in case it seems like the submitter is not clear on what to do. We want to make the process fun and exciting for new contributors.\hypertarget{md_lib_2libwconr_2build_2__deps_2curl-src_2docs_2CODE__REVIEW_autotoc_md1494}{}\doxysection{\texorpdfstring{Encourage consistency}{Encourage consistency}}\label{md_lib_2libwconr_2build_2__deps_2curl-src_2docs_2CODE__REVIEW_autotoc_md1494}
Make sure new code is written in a similar style as existing code. Naming, logic, conditions, etc.\hypertarget{md_lib_2libwconr_2build_2__deps_2curl-src_2docs_2CODE__REVIEW_autotoc_md1495}{}\doxysection{\texorpdfstring{Are pointers always non-\/\+NULL?}{Are pointers always non-\/\+NULL?}}\label{md_lib_2libwconr_2build_2__deps_2curl-src_2docs_2CODE__REVIEW_autotoc_md1495}
If a function or code rely on pointers being non-\/\+NULL, take an extra look if that seems to be a fair assessment.\hypertarget{md_lib_2libwconr_2build_2__deps_2curl-src_2docs_2CODE__REVIEW_autotoc_md1496}{}\doxysection{\texorpdfstring{Asserts}{Asserts}}\label{md_lib_2libwconr_2build_2__deps_2curl-src_2docs_2CODE__REVIEW_autotoc_md1496}
Conditions that should never be false can be verified with {\ttfamily \doxylink{curl__setup__once_8h_a23d7b88872d6ead46c978b567908d587}{DEBUGASSERT()}} calls to get caught in tests and debugging easier, while not having an impact on final or release builds.\hypertarget{md_lib_2libwconr_2build_2__deps_2curl-src_2docs_2CODE__REVIEW_autotoc_md1497}{}\doxysection{\texorpdfstring{Memory allocation}{Memory allocation}}\label{md_lib_2libwconr_2build_2__deps_2curl-src_2docs_2CODE__REVIEW_autotoc_md1497}
Can the mallocs be avoided? Do not introduce mallocs in any hot paths. If there are (new) mallocs, can they be combined into fewer calls?

Are all allocations handled in error paths to avoid leaks and crashes?\hypertarget{md_lib_2libwconr_2build_2__deps_2curl-src_2docs_2CODE__REVIEW_autotoc_md1498}{}\doxysection{\texorpdfstring{Thread-\/safety}{Thread-\/safety}}\label{md_lib_2libwconr_2build_2__deps_2curl-src_2docs_2CODE__REVIEW_autotoc_md1498}
We do not like static variables as they break thread-\/safety and prevent functions from being reentrant.\hypertarget{md_lib_2libwconr_2build_2__deps_2curl-src_2docs_2CODE__REVIEW_autotoc_md1499}{}\doxysection{\texorpdfstring{Should features be {\ttfamily \#ifdef}ed?}{Should features be {\ttfamily \#ifdef}ed?}}\label{md_lib_2libwconr_2build_2__deps_2curl-src_2docs_2CODE__REVIEW_autotoc_md1499}
Features and functionality may not be present everywhere and should therefore be {\ttfamily \#ifdef}ed. Additionally, some features should be possible to switch on/off in the build.

Write {\ttfamily \#ifdef}s to be as little of a "{}maze"{} as possible.\hypertarget{md_lib_2libwconr_2build_2__deps_2curl-src_2docs_2CODE__REVIEW_autotoc_md1500}{}\doxysection{\texorpdfstring{Does it look portable enough?}{Does it look portable enough?}}\label{md_lib_2libwconr_2build_2__deps_2curl-src_2docs_2CODE__REVIEW_autotoc_md1500}
curl runs "{}everywhere"{}. Does the code take a reasonable stance and enough precautions to be possible to build and run on most platforms?

Remember that we live by C89 restrictions.\hypertarget{md_lib_2libwconr_2build_2__deps_2curl-src_2docs_2CODE__REVIEW_autotoc_md1501}{}\doxysection{\texorpdfstring{Tests and testability}{Tests and testability}}\label{md_lib_2libwconr_2build_2__deps_2curl-src_2docs_2CODE__REVIEW_autotoc_md1501}
New features should be added in conjunction with one or more test cases. Ideally, functions should also be written so that unit tests can be done to test individual functions.\hypertarget{md_lib_2libwconr_2build_2__deps_2curl-src_2docs_2CODE__REVIEW_autotoc_md1502}{}\doxysection{\texorpdfstring{Documentation}{Documentation}}\label{md_lib_2libwconr_2build_2__deps_2curl-src_2docs_2CODE__REVIEW_autotoc_md1502}
New features or changes to existing functionality {\bfseries{must}} be accompanied by updated documentation. Submitting that in a separate follow-\/up pull request is not OK. A code review must also verify that the submitted documentation update matches the code submission.

English is not everyone\textquotesingle{}s first language, be mindful of this and help the submitter improve the text if it needs a rewrite to read better.\hypertarget{md_lib_2libwconr_2build_2__deps_2curl-src_2docs_2CODE__REVIEW_autotoc_md1503}{}\doxysection{\texorpdfstring{Code should not be hard to understand}{Code should not be hard to understand}}\label{md_lib_2libwconr_2build_2__deps_2curl-src_2docs_2CODE__REVIEW_autotoc_md1503}
Source code should be written to maximize readability and be easy to understand.\hypertarget{md_lib_2libwconr_2build_2__deps_2curl-src_2docs_2CODE__REVIEW_autotoc_md1504}{}\doxysection{\texorpdfstring{Functions should not be large}{Functions should not be large}}\label{md_lib_2libwconr_2build_2__deps_2curl-src_2docs_2CODE__REVIEW_autotoc_md1504}
A single function should never be large as that makes it hard to follow and understand all the exit points and state changes. Some existing functions in curl certainly violate this ground rule but when reviewing new code we should propose splitting into smaller functions.\hypertarget{md_lib_2libwconr_2build_2__deps_2curl-src_2docs_2CODE__REVIEW_autotoc_md1505}{}\doxysection{\texorpdfstring{Duplication is evil}{Duplication is evil}}\label{md_lib_2libwconr_2build_2__deps_2curl-src_2docs_2CODE__REVIEW_autotoc_md1505}
Anything that looks like duplicated code is a red flag. Anything that seems to introduce code that we {\itshape should} already have or provide needs a closer check.\hypertarget{md_lib_2libwconr_2build_2__deps_2curl-src_2docs_2CODE__REVIEW_autotoc_md1506}{}\doxysection{\texorpdfstring{Sensitive data}{Sensitive data}}\label{md_lib_2libwconr_2build_2__deps_2curl-src_2docs_2CODE__REVIEW_autotoc_md1506}
When credentials are involved, take an extra look at what happens with this data. Where it comes from and where it goes.\hypertarget{md_lib_2libwconr_2build_2__deps_2curl-src_2docs_2CODE__REVIEW_autotoc_md1507}{}\doxysection{\texorpdfstring{Variable types differ}{Variable types differ}}\label{md_lib_2libwconr_2build_2__deps_2curl-src_2docs_2CODE__REVIEW_autotoc_md1507}
{\ttfamily size\+\_\+t} is not a fixed size. {\ttfamily time\+\_\+t} can be signed or unsigned and have different sizes. Relying on variable sizes is a red flag.

Also remember that endianness and \texorpdfstring{$>$}{>}= 32 bit accesses to unaligned addresses are problematic areas.\hypertarget{md_lib_2libwconr_2build_2__deps_2curl-src_2docs_2CODE__REVIEW_autotoc_md1508}{}\doxysection{\texorpdfstring{Integer overflows}{Integer overflows}}\label{md_lib_2libwconr_2build_2__deps_2curl-src_2docs_2CODE__REVIEW_autotoc_md1508}
Be careful about integer overflows. Some variable types can be either 32 bit or 64 bit. Integer overflows must be detected and acted on {\itshape before} they happen.\hypertarget{md_lib_2libwconr_2build_2__deps_2curl-src_2docs_2CODE__REVIEW_autotoc_md1509}{}\doxysection{\texorpdfstring{Dangerous use of functions}{Dangerous use of functions}}\label{md_lib_2libwconr_2build_2__deps_2curl-src_2docs_2CODE__REVIEW_autotoc_md1509}
Maybe use of {\ttfamily \doxylink{curl__memory_8h_aa568500a9ca507b5a53de5372c81f26a}{realloc()}} should rather use the dynbuf functions?

Do not allow new code that grows buffers without using dynbuf.

Use of C functions that rely on a terminating zero must only be used on data that really do have a null-\/terminating zero.\hypertarget{md_lib_2libwconr_2build_2__deps_2curl-src_2docs_2CODE__REVIEW_autotoc_md1510}{}\doxysection{\texorpdfstring{Dangerous "{}data styles"{}}{Dangerous "{}data styles"{}}}\label{md_lib_2libwconr_2build_2__deps_2curl-src_2docs_2CODE__REVIEW_autotoc_md1510}
Make extra precautions and verify that memory buffers that need a terminating zero always have exactly that. Buffers {\itshape without} a null-\/terminator must not be used as input to string functions.\hypertarget{md_lib_2libwconr_2build_2__deps_2curl-src_2docs_2CODE__REVIEW_autotoc_md1511}{}\doxysection{\texorpdfstring{Commit messages}{Commit messages}}\label{md_lib_2libwconr_2build_2__deps_2curl-src_2docs_2CODE__REVIEW_autotoc_md1511}
Tightly coupled with a code review is making sure that the commit message is good. It is the responsibility of the person who merges the code to make sure that the commit message follows our standard (detailed in the \doxysectlink{md_lib_2libwconr_2build_2__deps_2curl-src_2docs_2CONTRIBUTE}{CONTRIBUTE}{0} document). This includes making sure the PR identifies related issues and giving credit to reporters and helpers.

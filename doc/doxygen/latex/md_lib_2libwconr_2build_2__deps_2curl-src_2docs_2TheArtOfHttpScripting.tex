\chapter{The Art Of Scripting HTTP Requests Using Curl }

\hypertarget{md_lib_2libwconr_2build_2__deps_2curl-src_2docs_2TheArtOfHttpScripting_autotoc_md1844}{}\doxysection{\texorpdfstring{Background}{Background}}\label{md_lib_2libwconr_2build_2__deps_2curl-src_2docs_2TheArtOfHttpScripting_autotoc_md1844}
This document assumes that you are familiar with HTML and general networking.

The increasing amount of applications moving to the web has made "{}\+HTTP  Scripting"{} more frequently requested and wanted. To be able to automatically extract information from the web, to fake users, to post or upload data to web servers are all important tasks today.

Curl is a command line tool for doing all sorts of URL manipulations and transfers, but this particular document will focus on how to use it when doing \doxylink{structHTTP}{HTTP} requests for fun and profit. I will assume that you know how to invoke {\ttfamily \doxylink{sessioninfo_8c_a6a59594ba3469ec6a1d56f6631e275e0}{curl} -\/-\/help} or {\ttfamily \doxylink{sessioninfo_8c_a6a59594ba3469ec6a1d56f6631e275e0}{curl} -\/-\/manual} to get basic information about it.

Curl is not written to do everything for you. It makes the requests, it gets the data, it sends data and it retrieves the information. You probably need to glue everything together using some kind of script language or repeated manual invokes.\hypertarget{md_lib_2libwconr_2build_2__deps_2curl-src_2docs_2TheArtOfHttpScripting_autotoc_md1845}{}\doxysection{\texorpdfstring{The HTTP Protocol}{The HTTP Protocol}}\label{md_lib_2libwconr_2build_2__deps_2curl-src_2docs_2TheArtOfHttpScripting_autotoc_md1845}
\doxylink{structHTTP}{HTTP} is the protocol used to fetch data from web servers. It is a simple protocol that is built upon TCP/\+IP. The protocol also allows information to get sent to the server from the client using a few different methods, as will be shown here.

\doxylink{structHTTP}{HTTP} is plain ASCII text lines being sent by the client to a server to request a particular action, and then the server replies a few text lines before the actual requested content is sent to the client.

The client, curl, sends an \doxylink{structHTTP}{HTTP} request. The request contains a method (like GET, POST, HEAD etc), a number of request headers and sometimes a request body. The \doxylink{structHTTP}{HTTP} server responds with a status line (indicating if things went well), response headers and most often also a response body. The "{}body"{} part is the plain data you requested, like the actual HTML or the image etc.\hypertarget{md_lib_2libwconr_2build_2__deps_2curl-src_2docs_2TheArtOfHttpScripting_autotoc_md1846}{}\doxysection{\texorpdfstring{See the Protocol}{See the Protocol}}\label{md_lib_2libwconr_2build_2__deps_2curl-src_2docs_2TheArtOfHttpScripting_autotoc_md1846}
Using curl\textquotesingle{}s option \href{https://curl.se/docs/manpage.html\#-v}{\texttt{{\ttfamily -\/-\/verbose}}} ({\ttfamily -\/v} as a short option) will display what kind of commands curl sends to the server, as well as a few other informational texts.

{\ttfamily -\/-\/\doxylink{next_8d_a30d811b7c0b95913359c2e0af9e774d2}{verbose}} is the single most useful option when it comes to debug or even understand the curl\texorpdfstring{$<$}{<}-\/\texorpdfstring{$>$}{>}server interaction.

Sometimes even {\ttfamily -\/-\/\doxylink{next_8d_a30d811b7c0b95913359c2e0af9e774d2}{verbose}} is not enough. Then \href{https://curl.se/docs/manpage.html\#-trace}{\texttt{{\ttfamily -\/-\/trace}}} and \href{https://curl.se/docs/manpage.html\#--trace-ascii}{\texttt{{\ttfamily -\/-\/trace-\/ascii}}} offer even more details as they show {\bfseries{everything}} curl sends and receives. Use it like this\+:

curl --trace-\/ascii debugdump.\+txt \href{http://www.example.com/}{\texttt{http\+://www.\+example.\+com/}}\hypertarget{md_lib_2libwconr_2build_2__deps_2curl-src_2docs_2TheArtOfHttpScripting_autotoc_md1847}{}\doxysection{\texorpdfstring{See the Timing}{See the Timing}}\label{md_lib_2libwconr_2build_2__deps_2curl-src_2docs_2TheArtOfHttpScripting_autotoc_md1847}
Many times you may wonder what exactly is taking all the time, or you just want to know the amount of milliseconds between two points in a transfer. For those, and other similar situations, the \href{https://curl.se/docs/manpage.html\#--trace-time}{\texttt{{\ttfamily -\/-\/trace-\/time}}} option is what you need. It will prepend the time to each trace output line\+:

curl --trace-\/ascii d.\+txt --trace-\/time \href{http://example.com/}{\texttt{http\+://example.\+com/}}\hypertarget{md_lib_2libwconr_2build_2__deps_2curl-src_2docs_2TheArtOfHttpScripting_autotoc_md1848}{}\doxysection{\texorpdfstring{See the Response}{See the Response}}\label{md_lib_2libwconr_2build_2__deps_2curl-src_2docs_2TheArtOfHttpScripting_autotoc_md1848}
By default curl sends the response to stdout. You need to redirect it somewhere to avoid that, most often that is done with {\ttfamily -\/o} or {\ttfamily -\/O}.\hypertarget{md_lib_2libwconr_2build_2__deps_2curl-src_2docs_2TheArtOfHttpScripting_autotoc_md1849}{}\doxysection{\texorpdfstring{URL}{URL}}\label{md_lib_2libwconr_2build_2__deps_2curl-src_2docs_2TheArtOfHttpScripting_autotoc_md1849}
\hypertarget{md_lib_2libwconr_2build_2__deps_2curl-src_2docs_2TheArtOfHttpScripting_autotoc_md1850}{}\doxysubsection{\texorpdfstring{Spec}{Spec}}\label{md_lib_2libwconr_2build_2__deps_2curl-src_2docs_2TheArtOfHttpScripting_autotoc_md1850}
The Uniform Resource Locator format is how you specify the address of a particular resource on the Internet. You know these, you have seen URLs like \href{https://curl.se}{\texttt{https\+://curl.\+se}} or \href{https://example.com}{\texttt{https\+://example.\+com}} a million times. RFC 3986 is the canonical spec. And yeah, the formal name is not URL, it is URI.\hypertarget{md_lib_2libwconr_2build_2__deps_2curl-src_2docs_2TheArtOfHttpScripting_autotoc_md1851}{}\doxysubsection{\texorpdfstring{Host}{Host}}\label{md_lib_2libwconr_2build_2__deps_2curl-src_2docs_2TheArtOfHttpScripting_autotoc_md1851}
The host name is usually resolved using DNS or your /etc/hosts file to an IP address and that is what curl will communicate with. Alternatively you specify the IP address directly in the URL instead of a name.

For development and other trying out situations, you can point to a different IP address for a host name than what would otherwise be used, by using curl\textquotesingle{}s \href{https://curl.se/docs/manpage.html\#--resolve}{\texttt{{\ttfamily -\/-\/resolve}}} option\+:

curl --resolve www.\+example.\+org\+:80\+:127.\+0.\+0.\+1 \href{http://www.example.org/}{\texttt{http\+://www.\+example.\+org/}}\hypertarget{md_lib_2libwconr_2build_2__deps_2curl-src_2docs_2TheArtOfHttpScripting_autotoc_md1852}{}\doxysubsection{\texorpdfstring{Port number}{Port number}}\label{md_lib_2libwconr_2build_2__deps_2curl-src_2docs_2TheArtOfHttpScripting_autotoc_md1852}
Each protocol curl supports operates on a default port number, be it over TCP or in some cases UDP. Normally you do not have to take that into consideration, but at times you run test servers on other ports or similar. Then you can specify the port number in the URL with a colon and a number immediately following the host name. Like when doing \doxylink{structHTTP}{HTTP} to port 1234\+:

curl \href{http://www.example.org:1234/}{\texttt{http\+://www.\+example.\+org\+:1234/}}

The port number you specify in the URL is the number that the server uses to offer its services. Sometimes you may use a proxy, and then you may need to specify that proxy\textquotesingle{}s port number separately from what curl needs to connect to the server. Like when using an \doxylink{structHTTP}{HTTP} proxy on port 4321\+:

curl --proxy \href{http://proxy.example.org:4321}{\texttt{http\+://proxy.\+example.\+org\+:4321}} \href{http://remote.example.org/}{\texttt{http\+://remote.\+example.\+org/}}\hypertarget{md_lib_2libwconr_2build_2__deps_2curl-src_2docs_2TheArtOfHttpScripting_autotoc_md1853}{}\doxysubsection{\texorpdfstring{User name and password}{User name and password}}\label{md_lib_2libwconr_2build_2__deps_2curl-src_2docs_2TheArtOfHttpScripting_autotoc_md1853}
Some services are setup to require \doxylink{structHTTP}{HTTP} authentication and then you need to provide name and password which is then transferred to the remote site in various ways depending on the exact authentication protocol used.

You can opt to either insert the user and password in the URL or you can provide them separately\+:

curl \href{http://user:password@example.org/}{\texttt{http\+://user\+:password@example.\+org/}}

or

curl -\/u user\+:password \href{http://example.org/}{\texttt{http\+://example.\+org/}}

You need to pay attention that this kind of \doxylink{structHTTP}{HTTP} authentication is not what is usually done and requested by user-\/oriented websites these days. They tend to use forms and cookies instead.\hypertarget{md_lib_2libwconr_2build_2__deps_2curl-src_2docs_2TheArtOfHttpScripting_autotoc_md1854}{}\doxysubsection{\texorpdfstring{Path part}{Path part}}\label{md_lib_2libwconr_2build_2__deps_2curl-src_2docs_2TheArtOfHttpScripting_autotoc_md1854}
The path part is just sent off to the server to request that it sends back the associated response. The path is what is to the right side of the slash that follows the host name and possibly port number.\hypertarget{md_lib_2libwconr_2build_2__deps_2curl-src_2docs_2TheArtOfHttpScripting_autotoc_md1855}{}\doxysection{\texorpdfstring{Fetch a page}{Fetch a page}}\label{md_lib_2libwconr_2build_2__deps_2curl-src_2docs_2TheArtOfHttpScripting_autotoc_md1855}
\hypertarget{md_lib_2libwconr_2build_2__deps_2curl-src_2docs_2TheArtOfHttpScripting_autotoc_md1856}{}\doxysubsection{\texorpdfstring{GET}{GET}}\label{md_lib_2libwconr_2build_2__deps_2curl-src_2docs_2TheArtOfHttpScripting_autotoc_md1856}
The simplest and most common request/operation made using \doxylink{structHTTP}{HTTP} is to GET a URL. The URL could itself refer to a web page, an image or a file. The client issues a GET request to the server and receives the document it asked for. If you issue the command line

curl \href{https://curl.se}{\texttt{https\+://curl.\+se}}

you get a web page returned in your terminal window. The entire HTML document that that URL holds.

All \doxylink{structHTTP}{HTTP} replies contain a set of response headers that are normally hidden, use curl\textquotesingle{}s \href{https://curl.se/docs/manpage.html\#-i}{\texttt{{\ttfamily -\/-\/include}}} ({\ttfamily -\/i}) option to display them as well as the rest of the document.\hypertarget{md_lib_2libwconr_2build_2__deps_2curl-src_2docs_2TheArtOfHttpScripting_autotoc_md1857}{}\doxysubsection{\texorpdfstring{HEAD}{HEAD}}\label{md_lib_2libwconr_2build_2__deps_2curl-src_2docs_2TheArtOfHttpScripting_autotoc_md1857}
You can ask the remote server for ONLY the headers by using the \href{https://curl.se/docs/manpage.html\#-I}{\texttt{{\ttfamily -\/-\/head}}} ({\ttfamily -\/\doxylink{md5_8c_ac0eafdc9ee161b71e7af98af736952fd}{I}}) option which will make curl issue a HEAD request. In some special cases servers deny the HEAD method while others still work, which is a particular kind of annoyance.

The HEAD method is defined and made so that the server returns the headers exactly the way it would do for a GET, but without a body. It means that you may see a {\ttfamily Content-\/\+Length\+:} in the response headers, but there must not be an actual body in the HEAD response.\hypertarget{md_lib_2libwconr_2build_2__deps_2curl-src_2docs_2TheArtOfHttpScripting_autotoc_md1858}{}\doxysubsection{\texorpdfstring{Multiple URLs in a single command line}{Multiple URLs in a single command line}}\label{md_lib_2libwconr_2build_2__deps_2curl-src_2docs_2TheArtOfHttpScripting_autotoc_md1858}
A single curl command line may involve one or many URLs. The most common case is probably to just use one, but you can specify any amount of URLs. Yes any. No limits. You will then get requests repeated over and over for all the given URLs.

Example, send two GET requests\+:

curl \href{http://url1.example.com}{\texttt{http\+://url1.\+example.\+com}} \href{http://url2.example.com}{\texttt{http\+://url2.\+example.\+com}}

If you use \href{https://curl.se/docs/manpage.html\#-d}{\texttt{{\ttfamily -\/-\/data}}} to POST to the URL, using multiple URLs means that you send that same POST to all the given URLs.

Example, send two POSTs\+:

curl --data name=curl \href{http://url1.example.com}{\texttt{http\+://url1.\+example.\+com}} \href{http://url2.example.com}{\texttt{http\+://url2.\+example.\+com}}\hypertarget{md_lib_2libwconr_2build_2__deps_2curl-src_2docs_2TheArtOfHttpScripting_autotoc_md1859}{}\doxysubsection{\texorpdfstring{Multiple HTTP methods in a single command line}{Multiple HTTP methods in a single command line}}\label{md_lib_2libwconr_2build_2__deps_2curl-src_2docs_2TheArtOfHttpScripting_autotoc_md1859}
Sometimes you need to operate on several URLs in a single command line and do different \doxylink{structHTTP}{HTTP} methods on each. For this, you will enjoy the \href{https://curl.se/docs/manpage.html\#-:}{\texttt{{\ttfamily -\/-\/next}}} option. It is basically a separator that separates a bunch of options from the next. All the URLs before {\ttfamily -\/-\/next} will get the same method and will get all the POST data merged into one.

When curl reaches the {\ttfamily -\/-\/next} on the command line, it will sort of reset the method and the POST data and allow a new set.

Perhaps this is best shown with a few examples. To send first a HEAD and then a GET\+:

curl -\/I \href{http://example.com}{\texttt{http\+://example.\+com}} --next \href{http://example.com}{\texttt{http\+://example.\+com}}

To first send a POST and then a GET\+:

curl -\/d score=10 \href{http://example.com/post.cgi}{\texttt{http\+://example.\+com/post.\+cgi}} --next \href{http://example.com/results.html}{\texttt{http\+://example.\+com/results.\+html}}\hypertarget{md_lib_2libwconr_2build_2__deps_2curl-src_2docs_2TheArtOfHttpScripting_autotoc_md1860}{}\doxysection{\texorpdfstring{HTML forms}{HTML forms}}\label{md_lib_2libwconr_2build_2__deps_2curl-src_2docs_2TheArtOfHttpScripting_autotoc_md1860}
\hypertarget{md_lib_2libwconr_2build_2__deps_2curl-src_2docs_2TheArtOfHttpScripting_autotoc_md1861}{}\doxysubsection{\texorpdfstring{Forms explained}{Forms explained}}\label{md_lib_2libwconr_2build_2__deps_2curl-src_2docs_2TheArtOfHttpScripting_autotoc_md1861}
Forms are the general way a website can present an HTML page with fields for the user to enter data in, and then press some kind of \textquotesingle{}OK\textquotesingle{} or \textquotesingle{}Submit\textquotesingle{} button to get that data sent to the server. The server then typically uses the posted data to decide how to act. Like using the entered words to search in a database, or to add the info in a bug tracking system, display the entered address on a map or using the info as a login-\/prompt verifying that the user is allowed to see what it is about to see.

Of course there has to be some kind of program on the server end to receive the data you send. You cannot just invent something out of the air.\hypertarget{md_lib_2libwconr_2build_2__deps_2curl-src_2docs_2TheArtOfHttpScripting_autotoc_md1862}{}\doxysubsection{\texorpdfstring{GET}{GET}}\label{md_lib_2libwconr_2build_2__deps_2curl-src_2docs_2TheArtOfHttpScripting_autotoc_md1862}
A GET-\/form uses the method GET, as specified in HTML like\+:


\begin{DoxyCode}{0}
\DoxyCodeLine{<form\ method="{}GET"{}\ action="{}junk.cgi"{}>}
\DoxyCodeLine{\ \ <input\ type=text\ name="{}birthyear"{}>}
\DoxyCodeLine{\ \ <input\ type=submit\ name=press\ value="{}OK"{}>}
\DoxyCodeLine{</form>}

\end{DoxyCode}


In your favorite browser, this form will appear with a text box to fill in and a press-\/button labeled "{}\+OK"{}. If you fill in \textquotesingle{}1905\textquotesingle{} and press the OK button, your browser will then create a new URL to get for you. The URL will get {\ttfamily junk.\+cgi?birthyear=1905\&press=OK} appended to the path part of the previous URL.

If the original form was seen on the page {\ttfamily www.\+example.\+com/when/birth.html}, the second page you will get will become {\ttfamily www.\+example.\+com/when/junk.cgi?birthyear=1905\&press=OK}.

Most search engines work this way.

To make curl do the GET form post for you, just enter the expected created URL\+:

curl "{}http\+://www.\+example.\+com/when/junk.\+cgi?birthyear=1905\&press=\+OK"{}\hypertarget{md_lib_2libwconr_2build_2__deps_2curl-src_2docs_2TheArtOfHttpScripting_autotoc_md1863}{}\doxysubsection{\texorpdfstring{POST}{POST}}\label{md_lib_2libwconr_2build_2__deps_2curl-src_2docs_2TheArtOfHttpScripting_autotoc_md1863}
The GET method makes all input field names get displayed in the URL field of your browser. That is generally a good thing when you want to be able to bookmark that page with your given data, but it is an obvious disadvantage if you entered secret information in one of the fields or if there are a large amount of fields creating a long and unreadable URL.

The \doxylink{structHTTP}{HTTP} protocol then offers the POST method. This way the client sends the data separated from the URL and thus you will not see any of it in the URL address field.

The form would look similar to the previous one\+:


\begin{DoxyCode}{0}
\DoxyCodeLine{<form\ method="{}POST"{}\ action="{}junk.cgi"{}>}
\DoxyCodeLine{\ \ <input\ type=text\ name="{}birthyear"{}>}
\DoxyCodeLine{\ \ <input\ type=submit\ name=press\ value="{}\ OK\ "{}>}
\DoxyCodeLine{</form>}

\end{DoxyCode}


And to use curl to post this form with the same data filled in as before, we could do it like\+:

curl --data "{}birthyear=1905\&press=\%20\+OK\%20"{} \href{http://www.example.com/when/junk.cgi}{\texttt{http\+://www.\+example.\+com/when/junk.\+cgi}}

This kind of POST will use the Content-\/\+Type {\ttfamily application/x-\/www-\/form-\/urlencoded} and is the most widely used POST kind.

The data you send to the server MUST already be properly encoded, curl will not do that for you. For example, if you want the data to contain a space, you need to replace that space with {\ttfamily \%20}, etc. Failing to comply with this will most likely cause your data to be received wrongly and messed up.

Recent curl versions can in fact url-\/encode POST data for you, like this\+:

curl --data-\/urlencode "{}name=\+I am Daniel"{} \href{http://www.example.com}{\texttt{http\+://www.\+example.\+com}}

If you repeat {\ttfamily -\/-\/\doxylink{structdata}{data}} several times on the command line, curl will concatenate all the given data pieces -\/ and put a {\ttfamily \&} symbol between each data segment.\hypertarget{md_lib_2libwconr_2build_2__deps_2curl-src_2docs_2TheArtOfHttpScripting_autotoc_md1864}{}\doxysubsection{\texorpdfstring{File Upload POST}{File Upload POST}}\label{md_lib_2libwconr_2build_2__deps_2curl-src_2docs_2TheArtOfHttpScripting_autotoc_md1864}
Back in late 1995 they defined an additional way to post data over \doxylink{structHTTP}{HTTP}. It is documented in the RFC 1867, why this method sometimes is referred to as RFC1867-\/posting.

This method is mainly designed to better support file uploads. A form that allows a user to upload a file could be written like this in HTML\+:


\begin{DoxyCode}{0}
\DoxyCodeLine{<form\ method="{}POST"{}\ enctype='multipart/form-\/data'\ action="{}upload.cgi"{}>}
\DoxyCodeLine{\ \ <input\ type=file\ name=upload>}
\DoxyCodeLine{\ \ <input\ type=submit\ name=press\ value="{}OK"{}>}
\DoxyCodeLine{</form>}

\end{DoxyCode}


This clearly shows that the Content-\/\+Type about to be sent is {\ttfamily multipart/form-\/data}.

To post to a form like this with curl, you enter a command line like\+:

curl --form upload=@localfilename --form press=OK \mbox{[}URL\mbox{]}\hypertarget{md_lib_2libwconr_2build_2__deps_2curl-src_2docs_2TheArtOfHttpScripting_autotoc_md1865}{}\doxysubsection{\texorpdfstring{Hidden Fields}{Hidden Fields}}\label{md_lib_2libwconr_2build_2__deps_2curl-src_2docs_2TheArtOfHttpScripting_autotoc_md1865}
A common way for HTML based applications to pass state information between pages is to add hidden fields to the forms. Hidden fields are already filled in, they are not displayed to the user and they get passed along just as all the other fields.

A similar example form with one visible field, one hidden field and one submit button could look like\+:


\begin{DoxyCode}{0}
\DoxyCodeLine{<form\ method="{}POST"{}\ action="{}foobar.cgi"{}>}
\DoxyCodeLine{\ \ <input\ type=text\ name="{}birthyear"{}>}
\DoxyCodeLine{\ \ <input\ type=hidden\ name="{}person"{}\ value="{}daniel"{}>}
\DoxyCodeLine{\ \ <input\ type=submit\ name="{}press"{}\ value="{}OK"{}>}
\DoxyCodeLine{</form>}

\end{DoxyCode}


To POST this with curl, you will not have to think about if the fields are hidden or not. To curl they are all the same\+:

curl --data "{}birthyear=1905\&press=\+OK\&person=daniel"{} \mbox{[}URL\mbox{]}\hypertarget{md_lib_2libwconr_2build_2__deps_2curl-src_2docs_2TheArtOfHttpScripting_autotoc_md1866}{}\doxysubsection{\texorpdfstring{Figure Out What A POST Looks Like}{Figure Out What A POST Looks Like}}\label{md_lib_2libwconr_2build_2__deps_2curl-src_2docs_2TheArtOfHttpScripting_autotoc_md1866}
When you are about to fill in a form and send it to a server by using curl instead of a browser, you are of course interested in sending a POST exactly the way your browser does.

An easy way to get to see this, is to save the HTML page with the form on your local disk, modify the \textquotesingle{}method\textquotesingle{} to a GET, and press the submit button (you could also change the action URL if you want to).

You will then clearly see the data get appended to the URL, separated with a {\ttfamily ?}-\/letter as GET forms are supposed to.\hypertarget{md_lib_2libwconr_2build_2__deps_2curl-src_2docs_2TheArtOfHttpScripting_autotoc_md1867}{}\doxysection{\texorpdfstring{HTTP upload}{HTTP upload}}\label{md_lib_2libwconr_2build_2__deps_2curl-src_2docs_2TheArtOfHttpScripting_autotoc_md1867}
\hypertarget{md_lib_2libwconr_2build_2__deps_2curl-src_2docs_2TheArtOfHttpScripting_autotoc_md1868}{}\doxysubsection{\texorpdfstring{PUT}{PUT}}\label{md_lib_2libwconr_2build_2__deps_2curl-src_2docs_2TheArtOfHttpScripting_autotoc_md1868}
Perhaps the best way to upload data to an \doxylink{structHTTP}{HTTP} server is to use PUT. Then again, this of course requires that someone put a program or script on the server end that knows how to receive an \doxylink{structHTTP}{HTTP} PUT stream.

Put a file to an \doxylink{structHTTP}{HTTP} server with curl\+:

curl --upload-\/file uploadfile \href{http://www.example.com/receive.cgi}{\texttt{http\+://www.\+example.\+com/receive.\+cgi}}\hypertarget{md_lib_2libwconr_2build_2__deps_2curl-src_2docs_2TheArtOfHttpScripting_autotoc_md1869}{}\doxysection{\texorpdfstring{HTTP Authentication}{HTTP Authentication}}\label{md_lib_2libwconr_2build_2__deps_2curl-src_2docs_2TheArtOfHttpScripting_autotoc_md1869}
\hypertarget{md_lib_2libwconr_2build_2__deps_2curl-src_2docs_2TheArtOfHttpScripting_autotoc_md1870}{}\doxysubsection{\texorpdfstring{Basic Authentication}{Basic Authentication}}\label{md_lib_2libwconr_2build_2__deps_2curl-src_2docs_2TheArtOfHttpScripting_autotoc_md1870}
\doxylink{structHTTP}{HTTP} Authentication is the ability to tell the server your username and password so that it can verify that you are allowed to do the request you are doing. The Basic authentication used in \doxylink{structHTTP}{HTTP} (which is the type curl uses by default) is {\bfseries{plain text}} based, which means it sends username and password only slightly obfuscated, but still fully readable by anyone that sniffs on the network between you and the remote server.

To tell curl to use a user and password for authentication\+:

curl --user name\+:password \href{http://www.example.com}{\texttt{http\+://www.\+example.\+com}}\hypertarget{md_lib_2libwconr_2build_2__deps_2curl-src_2docs_2TheArtOfHttpScripting_autotoc_md1871}{}\doxysubsection{\texorpdfstring{Other Authentication}{Other Authentication}}\label{md_lib_2libwconr_2build_2__deps_2curl-src_2docs_2TheArtOfHttpScripting_autotoc_md1871}
The site might require a different authentication method (check the headers returned by the server), and then \href{https://curl.se/docs/manpage.html\#--ntlm}{\texttt{{\ttfamily -\/-\/ntlm}}}, \href{https://curl.se/docs/manpage.html\#--digest}{\texttt{{\ttfamily -\/-\/digest}}}, \href{https://curl.se/docs/manpage.html\#--negotiate}{\texttt{{\ttfamily -\/-\/negotiate}}} or even \href{https://curl.se/docs/manpage.html\#--anyauth}{\texttt{{\ttfamily -\/-\/anyauth}}} might be options that suit you.\hypertarget{md_lib_2libwconr_2build_2__deps_2curl-src_2docs_2TheArtOfHttpScripting_autotoc_md1872}{}\doxysubsection{\texorpdfstring{Proxy Authentication}{Proxy Authentication}}\label{md_lib_2libwconr_2build_2__deps_2curl-src_2docs_2TheArtOfHttpScripting_autotoc_md1872}
Sometimes your \doxylink{structHTTP}{HTTP} access is only available through the use of an \doxylink{structHTTP}{HTTP} proxy. This seems to be especially common at various companies. An \doxylink{structHTTP}{HTTP} proxy may require its own user and password to allow the client to get through to the Internet. To specify those with curl, run something like\+:

curl --proxy-\/user proxyuser\+:proxypassword curl.\+se

If your proxy requires the authentication to be done using the NTLM method, use \href{https://curl.se/docs/manpage.html\#--proxy-ntlm}{\texttt{{\ttfamily -\/-\/proxy-\/ntlm}}}, if it requires Digest use \href{https://curl.se/docs/manpage.html\#--proxy-digest}{\texttt{{\ttfamily -\/-\/proxy-\/digest}}}.

If you use any one of these user+password options but leave out the password part, curl will prompt for the password interactively.\hypertarget{md_lib_2libwconr_2build_2__deps_2curl-src_2docs_2TheArtOfHttpScripting_autotoc_md1873}{}\doxysubsection{\texorpdfstring{Hiding credentials}{Hiding credentials}}\label{md_lib_2libwconr_2build_2__deps_2curl-src_2docs_2TheArtOfHttpScripting_autotoc_md1873}
Do note that when a program is run, its parameters might be possible to see when listing the running processes of the system. Thus, other users may be able to watch your passwords if you pass them as plain command line options. There are ways to circumvent this.

It is worth noting that while this is how \doxylink{structHTTP}{HTTP} Authentication works, many websites will not use this concept when they provide logins etc. See the Web Login chapter further below for more details on that.\hypertarget{md_lib_2libwconr_2build_2__deps_2curl-src_2docs_2TheArtOfHttpScripting_autotoc_md1874}{}\doxysection{\texorpdfstring{More HTTP Headers}{More HTTP Headers}}\label{md_lib_2libwconr_2build_2__deps_2curl-src_2docs_2TheArtOfHttpScripting_autotoc_md1874}
\hypertarget{md_lib_2libwconr_2build_2__deps_2curl-src_2docs_2TheArtOfHttpScripting_autotoc_md1875}{}\doxysubsection{\texorpdfstring{Referer}{Referer}}\label{md_lib_2libwconr_2build_2__deps_2curl-src_2docs_2TheArtOfHttpScripting_autotoc_md1875}
An \doxylink{structHTTP}{HTTP} request may include a \textquotesingle{}referer\textquotesingle{} field (yes it is misspelled), which can be used to tell from which URL the client got to this particular resource. Some programs/scripts check the referer field of requests to verify that this was not arriving from an external site or an unknown page. While this is a stupid way to check something so easily forged, many scripts still do it. Using curl, you can put anything you want in the referer-\/field and thus more easily be able to fool the server into serving your request.

Use curl to set the referer field with\+:

curl --referer \href{http://www.example.come}{\texttt{http\+://www.\+example.\+come}} \href{http://www.example.com}{\texttt{http\+://www.\+example.\+com}}\hypertarget{md_lib_2libwconr_2build_2__deps_2curl-src_2docs_2TheArtOfHttpScripting_autotoc_md1876}{}\doxysubsection{\texorpdfstring{User Agent}{User Agent}}\label{md_lib_2libwconr_2build_2__deps_2curl-src_2docs_2TheArtOfHttpScripting_autotoc_md1876}
Similar to the referer field, all \doxylink{structHTTP}{HTTP} requests may set the User-\/\+Agent field. It names what user agent (client) that is being used. Many applications use this information to decide how to display pages. Silly web programmers try to make different pages for users of different browsers to make them look the best possible for their particular browsers. They usually also do different kinds of Java\+Script etc.

At times, you will see that getting a page with curl will not return the same page that you see when getting the page with your browser. Then you know it is time to set the User Agent field to fool the server into thinking you are one of those browsers.

To make curl look like Internet Explorer 5 on a Windows 2000 box\+:

curl --user-\/agent "{}\+Mozilla/4.\+0 (compatible; MSIE 5.\+01; Windows NT 5.\+0)"{} \mbox{[}URL\mbox{]}

Or why not look like you are using Netscape 4.\+73 on an old Linux box\+:

curl --user-\/agent "{}\+Mozilla/4.\+73 \mbox{[}en\mbox{]} (\+X11; U; Linux 2.\+2.\+15 i686)"{} \mbox{[}URL\mbox{]}\hypertarget{md_lib_2libwconr_2build_2__deps_2curl-src_2docs_2TheArtOfHttpScripting_autotoc_md1877}{}\doxysubsection{\texorpdfstring{Redirects}{Redirects}}\label{md_lib_2libwconr_2build_2__deps_2curl-src_2docs_2TheArtOfHttpScripting_autotoc_md1877}
\hypertarget{md_lib_2libwconr_2build_2__deps_2curl-src_2docs_2TheArtOfHttpScripting_autotoc_md1878}{}\doxysubsection{\texorpdfstring{Location header}{Location header}}\label{md_lib_2libwconr_2build_2__deps_2curl-src_2docs_2TheArtOfHttpScripting_autotoc_md1878}
When a resource is requested from a server, the reply from the server may include a hint about where the browser should go next to find this page, or a new page keeping newly generated output. The header that tells the browser to redirect is {\ttfamily \doxylink{referer_8d_ae45fcf5b4d99b69e3c87c61b73d499b0}{Location}\+:}.

Curl does not follow {\ttfamily \doxylink{referer_8d_ae45fcf5b4d99b69e3c87c61b73d499b0}{Location}\+:} headers by default, but will simply display such pages in the same manner it displays all \doxylink{structHTTP}{HTTP} replies. It does however feature an option that will make it attempt to follow the {\ttfamily \doxylink{referer_8d_ae45fcf5b4d99b69e3c87c61b73d499b0}{Location}\+:} pointers.

To tell curl to follow a Location\+:

curl --location \href{http://www.example.com}{\texttt{http\+://www.\+example.\+com}}

If you use curl to POST to a site that immediately redirects you to another page, you can safely use \href{https://curl.se/docs/manpage.html\#-L}{\texttt{{\ttfamily -\/-\/location}}} ({\ttfamily -\/L}) and {\ttfamily -\/-\/\doxylink{structdata}{data}}/{\ttfamily -\/-\/form} together. Curl will only use POST in the first request, and then revert to GET in the following operations.\hypertarget{md_lib_2libwconr_2build_2__deps_2curl-src_2docs_2TheArtOfHttpScripting_autotoc_md1879}{}\doxysubsection{\texorpdfstring{Other redirects}{Other redirects}}\label{md_lib_2libwconr_2build_2__deps_2curl-src_2docs_2TheArtOfHttpScripting_autotoc_md1879}
Browsers typically support at least two other ways of redirects that curl does not\+: first the html may contain a meta refresh tag that asks the browser to load a specific URL after a set number of seconds, or it may use Java\+Script to do it.\hypertarget{md_lib_2libwconr_2build_2__deps_2curl-src_2docs_2TheArtOfHttpScripting_autotoc_md1880}{}\doxysection{\texorpdfstring{Cookies}{Cookies}}\label{md_lib_2libwconr_2build_2__deps_2curl-src_2docs_2TheArtOfHttpScripting_autotoc_md1880}
\hypertarget{md_lib_2libwconr_2build_2__deps_2curl-src_2docs_2TheArtOfHttpScripting_autotoc_md1881}{}\doxysubsection{\texorpdfstring{Cookie Basics}{Cookie Basics}}\label{md_lib_2libwconr_2build_2__deps_2curl-src_2docs_2TheArtOfHttpScripting_autotoc_md1881}
The way the web browsers do "{}client side state control"{} is by using cookies. Cookies are just names with associated contents. The cookies are sent to the client by the server. The server tells the client for what path and host name it wants the cookie sent back, and it also sends an expiration date and a few more properties.

When a client communicates with a server with a name and path as previously specified in a received cookie, the client sends back the cookies and their contents to the server, unless of course they are expired.

Many applications and servers use this method to connect a series of requests into a single logical session. To be able to use curl in such occasions, we must be able to record and send back cookies the way the web application expects them. The same way browsers deal with them.\hypertarget{md_lib_2libwconr_2build_2__deps_2curl-src_2docs_2TheArtOfHttpScripting_autotoc_md1882}{}\doxysubsection{\texorpdfstring{Cookie options}{Cookie options}}\label{md_lib_2libwconr_2build_2__deps_2curl-src_2docs_2TheArtOfHttpScripting_autotoc_md1882}
The simplest way to send a few cookies to the server when getting a page with curl is to add them on the command line like\+:

curl --cookie "{}name=\+Daniel"{} \href{http://www.example.com}{\texttt{http\+://www.\+example.\+com}}

Cookies are sent as common \doxylink{structHTTP}{HTTP} headers. This is practical as it allows curl to record cookies simply by recording headers. Record cookies with curl by using the \href{https://curl.se/docs/manpage.html\#-D}{\texttt{{\ttfamily -\/-\/dump-\/header}}} ({\ttfamily -\/D}) option like\+:

curl --dump-\/header headers\+\_\+and\+\_\+cookies \href{http://www.example.com}{\texttt{http\+://www.\+example.\+com}}

(Take note that the \href{https://curl.se/docs/manpage.html\#-c}{\texttt{{\ttfamily -\/-\/cookie-\/jar}}} option described below is a better way to store cookies.)

Curl has a full blown cookie parsing engine built-\/in that comes in use if you want to reconnect to a server and use cookies that were stored from a previous connection (or hand-\/crafted manually to fool the server into believing you had a previous connection). To use previously stored cookies, you run curl like\+:

curl --cookie stored\+\_\+cookies\+\_\+in\+\_\+file \href{http://www.example.com}{\texttt{http\+://www.\+example.\+com}}

Curl\textquotesingle{}s "{}cookie engine"{} gets enabled when you use the \href{https://curl.se/docs/manpage.html\#-b}{\texttt{{\ttfamily -\/-\/cookie}}} option. If you only want curl to understand received cookies, use {\ttfamily -\/-\/cookie} with a file that does not exist. Example, if you want to let curl understand cookies from a page and follow a location (and thus possibly send back cookies it received), you can invoke it like\+:

curl --cookie nada --location \href{http://www.example.com}{\texttt{http\+://www.\+example.\+com}}

Curl has the ability to read and write cookie files that use the same file format that Netscape and Mozilla once used. It is a convenient way to share cookies between scripts or invokes. The {\ttfamily -\/-\/cookie} ({\ttfamily -\/b}) switch automatically detects if a given file is such a cookie file and parses it, and by using the {\ttfamily -\/-\/cookie-\/jar} ({\ttfamily -\/c}) option you will make curl write a new cookie file at the end of an operation\+:

curl --cookie cookies.\+txt --cookie-\/jar newcookies.\+txt \textbackslash{} \href{http://www.example.com}{\texttt{http\+://www.\+example.\+com}}\hypertarget{md_lib_2libwconr_2build_2__deps_2curl-src_2docs_2TheArtOfHttpScripting_autotoc_md1883}{}\doxysection{\texorpdfstring{HTTPS}{HTTPS}}\label{md_lib_2libwconr_2build_2__deps_2curl-src_2docs_2TheArtOfHttpScripting_autotoc_md1883}
\hypertarget{md_lib_2libwconr_2build_2__deps_2curl-src_2docs_2TheArtOfHttpScripting_autotoc_md1884}{}\doxysubsection{\texorpdfstring{HTTPS is HTTP secure}{HTTPS is HTTP secure}}\label{md_lib_2libwconr_2build_2__deps_2curl-src_2docs_2TheArtOfHttpScripting_autotoc_md1884}
There are a few ways to do secure \doxylink{structHTTP}{HTTP} transfers. By far the most common protocol for doing this is what is generally known as HTTPS, \doxylink{structHTTP}{HTTP} over SSL. SSL encrypts all the data that is sent and received over the network and thus makes it harder for attackers to spy on sensitive information.

SSL (or TLS as the current version of the standard is called) offers a set of advanced features to do secure transfers over \doxylink{structHTTP}{HTTP}.

Curl supports encrypted fetches when built to use a TLS library and it can be built to use one out of a fairly large set of libraries -\/ {\ttfamily \doxylink{sessioninfo_8c_a6a59594ba3469ec6a1d56f6631e275e0}{curl} -\/V} will show which one your curl was built to use (if any!). To get a page from an HTTPS server, simply run curl like\+:

curl \href{https://secure.example.com}{\texttt{https\+://secure.\+example.\+com}}\hypertarget{md_lib_2libwconr_2build_2__deps_2curl-src_2docs_2TheArtOfHttpScripting_autotoc_md1885}{}\doxysubsection{\texorpdfstring{Certificates}{Certificates}}\label{md_lib_2libwconr_2build_2__deps_2curl-src_2docs_2TheArtOfHttpScripting_autotoc_md1885}
In the HTTPS world, you use certificates to validate that you are the one you claim to be, as an addition to normal passwords. Curl supports client-\/ side certificates. All certificates are locked with a pass phrase, which you need to enter before the certificate can be used by curl. The pass phrase can be specified on the command line or if not, entered interactively when curl queries for it. Use a certificate with curl on an HTTPS server like\+:

curl --cert mycert.\+pem \href{https://secure.example.com}{\texttt{https\+://secure.\+example.\+com}}

curl also tries to verify that the server is who it claims to be, by verifying the server\textquotesingle{}s certificate against a locally stored CA cert bundle. Failing the verification will cause curl to deny the connection. You must then use \href{https://curl.se/docs/manpage.html\#-k}{\texttt{{\ttfamily -\/-\/insecure}}} ({\ttfamily -\/k}) in case you want to tell curl to ignore that the server cannot be verified.

More about server certificate verification and ca cert bundles can be read in the \href{https://curl.se/docs/sslcerts.html}{\texttt{{\ttfamily SSLCERTS} document}}.

At times you may end up with your own CA cert store and then you can tell curl to use that to verify the server\textquotesingle{}s certificate\+:

curl --cacert ca-\/bundle.\+pem \href{https://example.com/}{\texttt{https\+://example.\+com/}}\hypertarget{md_lib_2libwconr_2build_2__deps_2curl-src_2docs_2TheArtOfHttpScripting_autotoc_md1886}{}\doxysection{\texorpdfstring{Custom Request Elements}{Custom Request Elements}}\label{md_lib_2libwconr_2build_2__deps_2curl-src_2docs_2TheArtOfHttpScripting_autotoc_md1886}
\hypertarget{md_lib_2libwconr_2build_2__deps_2curl-src_2docs_2TheArtOfHttpScripting_autotoc_md1887}{}\doxysubsection{\texorpdfstring{Modify method and headers}{Modify method and headers}}\label{md_lib_2libwconr_2build_2__deps_2curl-src_2docs_2TheArtOfHttpScripting_autotoc_md1887}
Doing fancy stuff, you may need to add or change elements of a single curl request.

For example, you can change the POST method to {\ttfamily \doxylink{request_8d_acd6013bd95a809f450e554606c0553d6}{PROPFIND}} and send the data as {\ttfamily Content-\/\+Type\+: text/xml} (instead of the default {\ttfamily Content-\/\+Type}) like this\+:

curl --data "{}$<$xml$>$"{} --header "{}\+Content-\/\+Type\+: text/xml"{} \textbackslash{} --request PROPFIND example.\+com

You can delete a default header by providing one without content. Like you can ruin the request by chopping off the {\ttfamily Host\+:} header\+:

curl --header "{}\+Host\+:"{} \href{http://www.example.com}{\texttt{http\+://www.\+example.\+com}}

You can add headers the same way. Your server may want a {\ttfamily Destination\+:} header, and you can add it\+:

curl --header "{}\+Destination\+: http\+://nowhere"{} \href{http://example.com}{\texttt{http\+://example.\+com}}\hypertarget{md_lib_2libwconr_2build_2__deps_2curl-src_2docs_2TheArtOfHttpScripting_autotoc_md1888}{}\doxysubsection{\texorpdfstring{More on changed methods}{More on changed methods}}\label{md_lib_2libwconr_2build_2__deps_2curl-src_2docs_2TheArtOfHttpScripting_autotoc_md1888}
It should be noted that curl selects which methods to use on its own depending on what action to ask for. {\ttfamily -\/d} will do POST, {\ttfamily -\/\doxylink{md5_8c_ac0eafdc9ee161b71e7af98af736952fd}{I}} will do HEAD and so on. If you use the \href{https://curl.se/docs/manpage.html\#-X}{\texttt{{\ttfamily -\/-\/request}}} / {\ttfamily -\/X} option you can change the method keyword curl selects, but you will not modify curl\textquotesingle{}s behavior. This means that if you for example use -\/d "{}data"{} to do a POST, you can modify the method to a {\ttfamily \doxylink{request_8d_acd6013bd95a809f450e554606c0553d6}{PROPFIND}} with {\ttfamily -\/X} and curl will still think it sends a POST . You can change the normal GET to a POST method by simply adding {\ttfamily -\/X POST} in a command line like\+:

curl -\/X POST \href{http://example.org/}{\texttt{http\+://example.\+org/}}

... but curl will still think and act as if it sent a GET so it will not send any request body etc.\hypertarget{md_lib_2libwconr_2build_2__deps_2curl-src_2docs_2TheArtOfHttpScripting_autotoc_md1889}{}\doxysection{\texorpdfstring{Web Login}{Web Login}}\label{md_lib_2libwconr_2build_2__deps_2curl-src_2docs_2TheArtOfHttpScripting_autotoc_md1889}
\hypertarget{md_lib_2libwconr_2build_2__deps_2curl-src_2docs_2TheArtOfHttpScripting_autotoc_md1890}{}\doxysubsection{\texorpdfstring{Some login tricks}{Some login tricks}}\label{md_lib_2libwconr_2build_2__deps_2curl-src_2docs_2TheArtOfHttpScripting_autotoc_md1890}
While not strictly just \doxylink{structHTTP}{HTTP} related, it still causes a lot of people problems so here\textquotesingle{}s the executive run-\/down of how the vast majority of all login forms work and how to login to them using curl.

It can also be noted that to do this properly in an automated fashion, you will most certainly need to script things and do multiple curl invokes etc.

First, servers mostly use cookies to track the logged-\/in status of the client, so you will need to capture the cookies you receive in the responses. Then, many sites also set a special cookie on the login page (to make sure you got there through their login page) so you should make a habit of first getting the login-\/form page to capture the cookies set there.

Some web-\/based login systems feature various amounts of Java\+Script, and sometimes they use such code to set or modify cookie contents. Possibly they do that to prevent programmed logins, like this manual describes how to... Anyway, if reading the code is not enough to let you repeat the behavior manually, capturing the \doxylink{structHTTP}{HTTP} requests done by your browsers and analyzing the sent cookies is usually a working method to work out how to shortcut the Java\+Script need.

In the actual {\ttfamily \texorpdfstring{$<$}{<}form\texorpdfstring{$>$}{>}} tag for the login, lots of sites fill-\/in random/session or otherwise secretly generated hidden tags and you may need to first capture the HTML code for the login form and extract all the hidden fields to be able to do a proper login POST. Remember that the contents need to be URL encoded when sent in a normal POST.\hypertarget{md_lib_2libwconr_2build_2__deps_2curl-src_2docs_2TheArtOfHttpScripting_autotoc_md1891}{}\doxysection{\texorpdfstring{Debug}{Debug}}\label{md_lib_2libwconr_2build_2__deps_2curl-src_2docs_2TheArtOfHttpScripting_autotoc_md1891}
\hypertarget{md_lib_2libwconr_2build_2__deps_2curl-src_2docs_2TheArtOfHttpScripting_autotoc_md1892}{}\doxysubsection{\texorpdfstring{Some debug tricks}{Some debug tricks}}\label{md_lib_2libwconr_2build_2__deps_2curl-src_2docs_2TheArtOfHttpScripting_autotoc_md1892}
Many times when you run curl on a site, you will notice that the site does not seem to respond the same way to your curl requests as it does to your browser\textquotesingle{}s.

Then you need to start making your curl requests more similar to your browser\textquotesingle{}s requests\+:


\begin{DoxyItemize}
\item Use the {\ttfamily -\/-\/trace-\/ascii} option to store fully detailed logs of the requests for easier analyzing and better understanding
\item Make sure you check for and use cookies when needed (both reading with {\ttfamily -\/-\/cookie} and writing with {\ttfamily -\/-\/cookie-\/jar})
\item Set user-\/agent (with \href{https://curl.se/docs/manpage.html\#-A}{\texttt{{\ttfamily -\/A}}}) to one like a recent popular browser does
\item Set referer (with \href{https://curl.se/docs/manpage.html\#-E}{\texttt{{\ttfamily -\/E}}}) like it is set by the browser
\item If you use POST, make sure you send all the fields and in the same order as the browser does it.
\end{DoxyItemize}\hypertarget{md_lib_2libwconr_2build_2__deps_2curl-src_2docs_2TheArtOfHttpScripting_autotoc_md1893}{}\doxysubsection{\texorpdfstring{Check what the browsers do}{Check what the browsers do}}\label{md_lib_2libwconr_2build_2__deps_2curl-src_2docs_2TheArtOfHttpScripting_autotoc_md1893}
A good helper to make sure you do this right, is the web browsers\textquotesingle{} developers tools that let you view all headers you send and receive (even when using HTTPS).

A more raw approach is to capture the \doxylink{structHTTP}{HTTP} traffic on the network with tools such as Wireshark or tcpdump and check what headers that were sent and received by the browser. (HTTPS forces you to use {\ttfamily SSLKEYLOGFILE} to do that.)
